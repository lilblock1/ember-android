# Feasibility assessment — 2026-10-24

## Finding

A direct, demonstrated AOT port of the unmodified Minecraft Java client has **not** been
established. A native Android shell is feasible and implemented here. Game execution is
the unresolved research problem. ARM64 describes the instruction set; Android's platform
ABI, libraries, lifecycle and graphics interfaces still differ from desktop ARM64.

The initial 1.20.4 metadata was fetched from Mojang's public version manifest and verified
against its SHA-1 entry. It specifies Java 17 and LWJGL 3.3.2 modules including GLFW,
OpenGL, OpenAL, jemalloc, STB and tinyfd. Its listed native classifiers are desktop targets;
none identify Android. This observation comes from metadata, not execution of the client.
The metadata-only report is in `docs/evidence/metadata-1.20.4.json`.

## Options

| Approach | Potential benefit | Blocking evidence still needed | Licensing/maintenance |
|---|---|---|---|
| AOT to Android ARM64 | Native machine-code game execution | Supported Android/Bionic toolchain; full Java 17 services; reflection/JNI/resources; class initialization; native dependency replacement | Local conversion/distribution permissions unresolved; per-version metadata and ABI maintenance |
| Java classfiles → DEX → ART | Uses Android managed runtime and platform integration | Java SE compatibility, unsupported dynamic behavior, LWJGL JNI adaptation, classloading/native library behavior | Preserve originals; toolchain/third-party notices; runtime execution must be described honestly |
| Android OpenJDK plus native bridges | Potentially closer Java SE behavior | Bionic port, GLES/Vulkan translation, input/audio and actual physical-device proof | OpenJDK GPLv2 + Classpath Exception review; still a JVM, conflicts with strict goal |
| Rewrite game in C++ | Separate native program | Would require rebuilding proprietary behavior/source | Does not meet the requirement to run the official client; not pursued |

GraalVM Native Image includes only elements found reachable; dynamic reflection, resources
and JNI may require explicit metadata. Its current SDK lists an Android AArch64 platform
type, which is useful research evidence but does **not** prove that this client or all of its
dependencies can be built or run there. Sources: [dynamic features](https://www.graalvm.org/latest/reference-manual/native-image/dynamic-features/),
[platform API](https://www.graalvm.org/sdk/javadoc/org/graalvm/nativeimage/package-summary.html).

Android ART executes DEX with managed runtime services and AOT/JIT compilation.
It is not a desktop Java SE implementation merely because both use Java bytecode concepts.
Source: [Android platform architecture](https://developer.android.com/guide/platform).

LWJGL publishes desktop native libraries and lists supported desktop OS/architecture targets;
Android is not listed in the checked README. Linux ARM64 binaries must not be treated as
Android binaries. Source: [LWJGL upstream](https://github.com/LWJGL/lwjgl3/blob/master/README.md).

## Graphics and platform proof needed

GLFW window/context/event semantics must be mapped onto Android surfaces and lifecycle.
Desktop OpenGL calls and shaders need a sufficiently complete compatibility implementation;
GLES is not a drop-in implementation. Vulkan could underlie a translator, but Minecraft's
desktop GL calls do not become Vulkan by changing the surface. Investigate [Mesa Zink](https://docs.mesa3d.org/drivers/zink.html)
and its device/extension requirements before selecting it. No Mesa/ANGLE/LWJGL code is bundled.
OpenAL, native allocators, dialogs, filesystem assumptions, threads and Java native memory
access need separate audits. Shader and arbitrary mod compatibility are unproven.

The current C++ probe tests only a native surface, context callbacks and a touch queue.
The classfile audit detects selected desktop/JNI references in an original fixture and can
inventory an already-owned local JAR. It is conservative and cannot prove compatibility,
especially for reflection, generated bytecode or runtime-loaded dependencies.
The separate [runtime laboratory](RUNTIME_LAB.md) now builds an original Java 17 DEX,
reflection and registered-JNI test APK. Both tests passed on S25+. The separate LWJGL
subset passed its offscreen tests and visible pixel readback. No AOT route or actual client
execution has been demonstrated.

## API and licensing assessment

Microsoft documents native/mobile authorization code + PKCE. The foundation uses AppAuth,
a public-client flow and no client secret. Register an app and the exact redirect before
using it. Source: [Microsoft protocol documentation](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).

No project client ID, registration record or written Minecraft API approval was provided.
Authorization is therefore **unverified**, not implicitly granted by public documentation.
Xbox website sign-in documentation describes provisioning and U-token/XSTS stages, but a
confidential website sample is not an Android public-client authorization grant. Source:
[Xbox service sign-in](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/fundamentals/s2s-auth-calls/service-authentication/live-website-authentication).

The linked [Minecraft application information URL](https://aka.ms/AppRegInfo) could not be
read successfully during this review; the related support page returned no substantive
guidance. No authoritative current endpoint/schema documentation sufficient to validate
permanent vs subscription Java ownership was obtained. Do not infer a contract from
community reports or hard-code entitlement names as proof. Obtain current guidance from
Minecraft support for this project's own client ID. The staged Xbox/Minecraft adapters now
exist and pass nine mock tests; live use remains disabled pending approval.

The EULA permits certain original modifications/tools and restricts distribution of game
software or modified game versions. It also requires authorized download sources. Ownership
does not settle whether distributing a translated game image is permitted. This assessment
is a release blocker record, not a legal clearance. Obtain specific clarification before
distributing translated/modified binaries. Sources: [current EULA](https://www.minecraft.net/en-us/eula),
[usage guidelines](https://www.minecraft.net/en-us/usage-guidelines).

## Next experiments, in order

1. Confirm application registration and Minecraft API approval, supported mobile scopes,
   entitlement semantics, subscription expiry and offline-use rules.
2. Inventory an entitled local 1.20.4 client plus dependencies without changing originals.
3. Prove a small original Java 17 reflection/JNI/classloading fixture with the chosen AOT or
   ART route on ARM64 Android; record limitations. No route is selected yet.
4. Implement the minimum LWJGL/GLFW/GL/native audio bridges and test offscreen rendering,
   context loss and input before passing them to the real client.
5. Launch that client to its actual main menu and world on physical hardware with logs and
   saves as evidence. Keep every first-playable box unchecked until each test passes.
